PRISM SECURITY AUDIT — CODEX PERSISTENT INSTRUCTIONS / STATUS

Purpose:
Maintain a persistent, authoritative security-audit status for the PRISM repository. This status must survive context changes and prevent completed findings from being re-audited unnecessarily or pending findings from being accidentally skipped.

GENERAL RULES
1. Treat this file/instructions as the source of truth for audit progress unless a newer explicit audit report supersedes it.
2. Never claim a finding is fixed or closed without evidence from:
   - regression tests,
   - relevant broader test suites,
   - diff/worktree inspection,
   - and an independent closure review where required.
3. Preserve the distinction between:
   - VALIDATED / CONFIRMED
   - REMEDIATION IN PROGRESS
   - FIXED / READY FOR CLOSURE
   - CLOSED / INDEPENDENTLY VERIFIED
   - NOT CONFIRMED
   - PENDING VALIDATION
4. Do not modify unrelated pre-existing working-tree changes.
5. For each finding, work one finding at a time:
   VALIDATE -> RED TESTS -> FIX -> GREEN TESTS -> ALTERNATE-PATH REVIEW -> INDEPENDENT CLOSURE REVIEW.
6. Do not silently reopen a CLOSED finding because of an unrelated observation. Create/track a separate finding unless the new issue directly defeats the closed security property.
7. Keep exact test baselines from the relevant audit report. Do not assume one universal integration-test count.

AUDIT PROCESS FOR EVERY PENDING FINDING

Phase 1 — Validation
- Read the relevant route/helper/schema/database code.
- Trace authentication, authorization, tenant scoping, input validation, DB writes/reads, downstream effects.
- Search repo-wide for alternate paths.
- Build a minimal isolated proof.
- Add regression tests only after understanding the vulnerable behavior.
- Run them against the vulnerable implementation and record RED results.
- Run relevant existing tests and record the baseline.
- Do NOT fix production code during validation.

Phase 2 — Remediation
Only after confirmation:
- Propose the smallest safe fix.
- Preserve legitimate frontend/API behavior.
- Implement regression tests for every confirmed attack path.
- Avoid touching unrelated files or pre-existing dirty worktree changes.

Phase 3 — Verification
- Run dedicated regression suite.
- Run relevant existing targeted suites.
- Run full unit suite.
- Run integration suite and compare exact failures to baseline.
- Search for alternate mutation/read paths.
- Inspect git diff.
- Confirm no unrelated files were changed.

Phase 4 — Independent Closure Review
A separate review must challenge the fix:
- Reproduce original exploit attempts.
- Search for sibling/alternate routes.
- Test tenant boundaries and role boundaries.
- Verify downstream side effects.
- Confirm frontend compatibility.
- Confirm no test was weakened.
- Only then mark CLOSED.
