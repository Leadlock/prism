# Okta Connector

## 1. Overview

- **Proposed `integrations.category`**: `identity`
- **Proposed `integrations.key`**: `okta`
- **Proposed `integrations.auth_type`**: `oauth2`

Okta is the identity provider (IdP) / SSO and directory service. This connector reads user, group, application-assignment, policy (MFA, password, sign-on), admin-role, and System Log data from a customer's Okta org to evidence identity and access-management controls (ISO 27001 Annex A.9), cryptography/authentication controls (A.9.4), and monitoring/logging (A.12.4).

Scope for v1: read-only checks against the Okta Management API (Users, Groups, Apps, Policies) and the System Log API. No write access is required.

## 2. Authentication

**`auth_type`: `oauth2`** (recommended over `api_key`)

Okta supports two authentication modes for API access:

1. **SSWS API token** (`api_key`) — generated by an admin user in the Admin Console, sent as an `Authorization: SSWS {token}` header. Simple to set up, but Okta explicitly recommends against it for new integrations: the token is a long-lived bearer credential tied to the creating admin's own privileges (not independently scoped), it has no expiry beyond a rolling inactivity window, and if that admin's account is later deprovisioned or demoted the token silently breaks or over-grants, with no per-token audit trail distinct from the admin's own actions.
2. **OAuth 2.0 client credentials via a Service App** (`oauth2`) — Okta's current recommendation for machine-to-machine integrations. The service app is its own principal (not tied to a human admin's account lifecycle), authenticates via a public/private key pair (`private_key_jwt` — the only supported client-authentication method for OAuth service apps), and is granted **fine-grained, explicitly-enumerated scopes** (`okta.users.read`, `okta.groups.read`, etc.) rather than inheriting a person's full admin privilege set.

**Recommendation: `oauth2`.** Reasoning: least privilege (scopes are enumerated per-resource-per-operation rather than "whatever this admin can do"), independent credential lifecycle (a service app survives the creating admin leaving, and is revocable/rotatable on its own key pair without touching any human account), short-lived tokens (access tokens are ~1 hour, versus an SSWS token that's effectively a standing secret), and it is Okta's documented current-best-practice path for new integrations — the SSWS API token model is legacy and Okta discourages new production usage of it.

### Setup steps (Okta Admin Console)

1. Sign in to the Okta Admin Console with Super Admin privileges (only Super Admin can grant OAuth API scopes to a service app — see step 5).
2. Go to **Applications > Applications > Create App Integration**. Select **API Services** as the sign-in method, name it (e.g. "Prism Compliance Reader"), and save.
3. On the new app's **General** tab, note the **Client ID**.
4. Under **Client Credentials**, click **Edit**, select **Public key / Private key** as the client authentication method. Generate a key pair (Okta can generate and store it, or accept an externally-generated public key/JWKS URL). If Okta generates the key: copy the private key immediately — it is shown only once. Store the private key as `secret.privateKey`.
5. Go to the app's **Okta API Scopes** tab and **Grant** each scope this connector needs (only a Super Admin can perform this grant):
   - `okta.users.read` — user inventory, status, profile, credential/factor enrollment summary.
   - `okta.groups.read` — group membership, used for access-review and role-mapping checks.
   - `okta.apps.read` — application catalog and per-app user/group assignments.
   - `okta.policies.read` — MFA enrollment/sign-on policies, password policies, authenticator enrollment policies.
   - `okta.logs.read` — System Log API access for sign-in/audit and anomaly data.
   - `okta.roles.read` — administrator role assignments (standard and custom admin roles), for admin-role review.
6. Under **Admin roles** (on the app itself), assign the minimum admin role needed for the granted scopes to actually resolve data — typically a custom, read-only admin role scoped to the required resource sets, rather than Super Admin, following least-privilege even at the role-assignment layer.
7. Record the org's **Okta domain** (e.g. `yourcompany.okta.com` or a custom domain) as `config.oktaDomain`.

### `config` shape (non-secret, stored on `integration_connections.config`)

```json
{
  "oktaDomain": "yourcompany.okta.com",
  "clientId": "0oa1b2c3d4e5f6g7h8i9"
}
```

### `secret` shape (encrypted, stored via `integration_credentials`)

```json
{
  "privateKey": "-----BEGIN PRIVATE KEY-----\n...\n-----END PRIVATE KEY-----"
}
```

The connector builds a signed JWT (`iss`/`sub` = clientId, `aud` = `https://{oktaDomain}/oauth2/v1/token`, `exp` within 5 minutes, algorithm RS256/ES256) using `privateKey`, then `POST`s `grant_type=client_credentials`, `scope={space-separated scopes}`, `client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer`, `client_assertion={signed JWT}` to `https://{oktaDomain}/oauth2/v1/token` to obtain a ~1-hour bearer access token.

## 3. API Reference

- **Base URL**: `https://{config.oktaDomain}` (the org's own Okta domain — Okta is single-tenant-per-org with no separate regional API host the way CrowdStrike has; a custom domain, if configured, is used the same way).
- **Token endpoint**: `POST https://{oktaDomain}/oauth2/v1/token`.
- **Pagination**: cursor-based via the standard `Link` response header (`rel="next"`) on all list endpoints (`/api/v1/users`, `/api/v1/groups`, `/api/v1/apps`, etc.) — follow the `next` link until it's absent. The System Log endpoint (`/api/v1/logs`) always returns a `next` link (to support continuous polling) regardless of whether new data exists, so termination for that endpoint must be judged by an empty result page, not by the presence/absence of `next`.
- **Rate limits**: enforced per-org, per-endpoint (and in some cases per-endpoint-per-user), varying by subscription tier and endpoint; responses include `X-Rate-Limit-Limit`, `X-Rate-Limit-Remaining`, and `X-Rate-Limit-Reset` headers — back off using these rather than a hardcoded assumption. The System Log endpoint has been observed around 120 requests/minute on trial-tier orgs; production tiers vary and should be read from response headers rather than assumed.
- **Key endpoints**:
  - `GET /api/v1/users` — user inventory (`status`, `created`, `lastLogin`, profile attributes).
  - `GET /api/v1/users/{userId}/factors` — enrolled MFA factors per user (for a per-user 2FA-enrollment cross-check beyond the org-wide policy check).
  - `GET /api/v1/groups` + `GET /api/v1/groups/{groupId}/users` — group definitions and membership.
  - `GET /api/v1/apps` + `GET /api/v1/apps/{appId}/users` / `.../groups` — application catalog and assignment.
  - `GET /api/v1/policies?type=MFA_ENROLL` / `?type=OKTA_SIGN_ON` / `?type=PASSWORD` — policy definitions and rules.
  - `GET /api/v1/iam/roles` / `GET /api/v1/users/{userId}/roles` — standard and custom admin role assignments.
  - `GET /api/v1/logs?since=...&filter=...` — System Log: authentication events, `eventType` (e.g. `policy.evaluate_sign_on`, `user.authentication.auth_via_mfa`), risk/behavior signals under `debugContext`/`securityContext` when Okta ThreatInsight or Behavior Detection is enabled.
- **Docs**: [Set up Okta for OAuth API access](https://developer.okta.com/docs/guides/set-up-oauth-api/main/) · [Implement OAuth for Okta with a service app](https://developer.okta.com/docs/guides/implement-oauth-for-okta-serviceapp/main/) · [Core Okta API](https://developer.okta.com/docs/reference/core-okta-api/) · [Okta rate limits](https://developer.okta.com/docs/reference/rate-limits/)

| `okta.policy.mfa_enforcement` | An MFA enrollment/sign-on policy is enforced for all users | critical | A.9.4.2 | Checks `GET /api/v1/policies?type=MFA_ENROLL` (and `OKTA_SIGN_ON` policy rules referencing MFA) has at least one active rule requiring MFA, with no group/user scoped out of coverage. | Configure an Okta Sign-On or MFA Enrollment policy requiring multi-factor authentication for all users, and remove exclusion groups that aren't explicitly justified. |

| `okta.group.privileged_group_membership_review` | Membership in privileged/admin-mapped groups is limited and reviewed | medium | A.9.2.3 | Checks `GET /api/v1/groups/{groupId}/users` for groups mapped to privileged application roles (e.g. an "AWS-Admins" or "Prod-DB-Access" group) against an expected roster. | Audit membership of privileged groups and remove users who no longer require the downstream access those groups grant. |
| `okta.app.deprovisioning_on_offboard` | Application access is automatically deprovisioned on user deactivation | high | A.9.2.6 | Checks recently deprovisioned users (`status eq "DEPROVISIONED"` in the trailing period) had their application assignments removed at or near deactivation time (via System Log `application.user_membership.remove` correlated to `user.lifecycle.deactivate`), rather than lingering. | Confirm Okta Lifecycle Management (or equivalent automation) is configured to deprovision app access immediately on user deactivation rather than relying on manual follow-up. |

## 6. Implementation Notes

- **Connector `key`**: `okta` (used in `registry.js`).
- **Suggested files**:
  - `api/src/connectors/okta/index.js` — exports `key`, `tests`, `testConnection()`, `runTests()`, mirroring `api/src/connectors/azure/index.js`'s structure (build a bearer-token-authenticated client, run each test's `run(clients)`).
  - `api/src/connectors/okta/credentials.js` — `resolveOktaCredentials({ authType, config, secret })`: validates `authType === "oauth2"`, signs a `private_key_jwt` client assertion (RS256, using a small JWT-signing utility rather than a full Okta SDK) and POSTs to `https://{config.oktaDomain}/oauth2/v1/token`, returns `{ accessToken, oktaDomain: config.oktaDomain }`. Re-fetch per run given the ~1 hour token lifetime.
  - `api/src/connectors/okta/client.js` — thin `fetch`-based wrapper handling `Link`-header pagination (generic across `/users`, `/groups`, `/apps`) and a separate log-cursor helper for `/api/v1/logs` (page until an empty result set rather than absence of `next`).
  - `api/src/connectors/okta/tests/users.js` — `checkFactorEnrollmentComplete`, `checkInactiveReview`.
  - `api/src/connectors/okta/tests/policies.js` — `checkMfaEnforcement`, `checkPasswordStrength`, `checkAnomalyPolicyReview`.
  - `api/src/connectors/okta/tests/roles.js` — `checkAdminAssignmentReview`, `checkPrivilegedGroupMembershipReview`.
  - `api/src/connectors/okta/tests/apps.js` — `checkAssignmentReview`, `checkDeprovisioningOnOffboard`.
  - `api/src/connectors/okta/tests/logs.js` — `checkAuditLoggingActive`.
- **Registry wiring**: add `import * as okta from "./okta/index.js";` and `[okta.key]: okta` to `api/src/connectors/registry.js`.
- **`testConnection()`**: perform the client-credentials token exchange (validates the JWT signature/key registration and client existence), then follow with a cheap `GET /api/v1/users?limit=1` to confirm the granted scopes actually resolve data (a token can be issued successfully even if a requested scope wasn't granted by a Super Admin, in which case the API call itself returns a 403 with an Okta-specific error code) — return `{ ok: true, externalAccountId: config.oktaDomain }`.
- **Domain/tenant consideration**: unlike CrowdStrike's small fixed set of regional hosts, every Okta customer has its own unique domain (`config.oktaDomain`) — there's no shared regional base URL to select from, so the connection setup UI should simply prompt for the org's Okta domain directly (with validation that it resolves and matches an Okta org, not an arbitrary hostname) rather than offering a region dropdown.
- **Custom domains**: some Okta orgs configure a custom domain (e.g. `login.customer.com`) instead of the default `*.okta.com` domain — `config.oktaDomain` should accept either, since both work identically as the API host once configured in Okta.
- **Scope-grant failure mode**: because only a Super Admin can grant `Okta API Scopes` to a service app (step 5 above), a common setup failure is a non-Super-Admin completing app creation but being unable to complete the scope grant — `testConnection` should surface a 403 on a granted-but-ungranted-scope call as "an Okta Super Admin must grant this app's API scopes under Okta API Scopes" rather than a generic auth failure.
